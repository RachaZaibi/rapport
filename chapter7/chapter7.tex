\section*{Introduction}
\addcontentsline{toc}{section}{Introduction }
Le Sprint 3 élève le système Parc Informatique FMM au niveau décisionnel et collaboratif en intégrant les services de notification, de reporting et de pilotage analytique. Cette étape est entièrement dédiée au web, avec une interface React, un backend Express, une base de données MySQL et Firebase FCM. Le focus porte sur la production de notifications temps réel, la mise à disposition d'un tableau de bord métier et l'export des données indispensables au suivi opérationnel.

\section{Objectifs du Sprint 3}
Les objectifs du Sprint 3 se concentrent sur :
\begin{itemize}
    \item l'implémentation des notifications Firebase FCM pour les événements critiques du ticketing ;
    \item la construction d'un tableau de bord Web consolidant les indicateurs du parc ;
    \item la génération de rapports métier et l'export des statistiques ;
    \item l'optimisation des performances API et frontend pour un accès rapide et participatif.
\end{itemize}

\section{Architecture et modélisation UML du Sprint 3}
\label{sec:uml_sprint3}
Le Sprint 3 introduit un sous-système analytique et de notification dont l'objectif est de transformer les événements métiers en informations décisionnelles. Les acteurs restent l'Administrateur, le Technicien et l'Utilisateur. Le système conserve sa structure web : React pour l'expérience utilisateur, Express pour le traitement applicatif, MySQL pour la persistance et Firebase FCM pour la distribution des notifications.

\subsubsection{Clarification : Modèles réels vs composants calculés}

Avant de présenter la modélisation, une clarification importante s'impose. Le Sprint 3 combine deux approches complémentaires :
\begin{itemize}
    \item \textbf{Modèles persistants} : Utilisateur, Équipement, Ticket, Intervention, Maintenance, Logiciel, Licence, Installation, Rapport, Transfer, Assignment (identiques aux sprints précédents).
    
    \item \textbf{Composants calculés en temps réel} : Le tableau de bord et les statistiques ne disposent pas de table dédiée. Au lieu de cela, le backend agrège les données pertinentes (tickets, maintenances, équipements) à la demande via les endpoints \texttt{GET /api/dashboard} et \texttt{GET /api/statistics}. Cette approche garantit des données toujours à jour sans surcharge de persistance.
    
    \item \textbf{Notifications} : Les notifications ne créent pas d'entité persistante. Firebase FCM envoie des notifications push directement aux dispositifs via les tokens stockés dans le champ \texttt{fcmToken} du modèle Utilisateur. Les événements métier (création de ticket, changement de statut) déclenchent l'envoi de notifications sans journalisation persistante des notifications elles-mêmes.
\end{itemize}

\subsection{Diagrammes de séquence Sprint 3}
Cette section décrit les scénarios dynamiques de notification et de reporting, en détaillant les échanges entre le frontend React, le backend Express, MySQL et Firebase FCM.

\subsubsection{Envoi d'une notification lors de la création d'un ticket}
Ce diagramme illustre le processus d'envoi d'une notification push lorsqu'un ticket est créé. Le backend enregistre le ticket dans MySQL, puis récupère les utilisateurs concernés (administrateur et techniciens assignés). Pour chacun d'eux, le backend émet une requête vers Firebase FCM avec leur token enregistré. Firebase pousse la notification vers les appareils cibles connectés au moment de l'événement. Aucune table de notification n'est créée : le système fonctionne en broadcast vers les tokens FCM stockés.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{chapter7/sequence_notification_creation_ticket.png}
    \caption{Diagramme de séquence d'envoi d'une notification lors de la création d'un ticket}
    \label{fig:sequence_notification_creation_ticket}
\end{figure}

\subsubsection{Notification lors d'un changement de statut}
Ce diagramme représente la mise à jour d'un ticket et l'émission d'une notification associée. Lorsqu'un technicien change le statut d'un ticket (par ex., passage en cours de traitement ou résolu), le backend persiste le nouvel état dans MySQL, récupère l'utilisateur ayant créé le ticket, et envoie une notification Firebase FCM au token de cet utilisateur. Comme pour la création de ticket, aucune entité Notification n'est persistée.

\subsubsection{Consultation du tableau de bord}
Ce diagramme présente la consultation du tableau de bord web par un administrateur. Le backend reçoit la requête GET /api/dashboard, puis agrège les données de MySQL en calculant dynamiquement les indicateurs clés : nombre de tickets ouverts/fermés/en cours, taux de résolution, équipements en panne, maintenances à venir, etc. Ces indicateurs sont construits chaque fois que le dashboard est consulté, sans table Dashboard persistante. Les données sont retournées en JSON et affichées par le frontend React.

Ce diagramme montre comment le système prépare un fichier d'export statistique. Lorsqu'un utilisateur demande l'export via GET /api/statistics/export, le backend requête MySQL pour récupérer les données brutes (équipements, tickets, maintenances), effectue les agrégations statistiques en mémoire (sans table Statistique), puis génère un fichier CSV ou Excel. \section{Tableaux de bord et reporting Web}
L'interface web du Sprint 3 fournit un tableau de bord centralisé regroupant les principaux indicateurs de santé du parc, les tickets critiques, les maintenances planifiées, les équipements hors service et les taux de résolution. Le dashboard est conçu pour être consulté par l'administrateur et le responsable technique, avec des filtres sur les périodes, les catégories d'équipements et les priorités. Les indicateurs sont calculés en temps réel lors de chaque consultation, ce qui garantit des données toujours cohérentes avec l'état de la base de données.

\section{Optimisation des performances}
Le Sprint 3 a porté une attention particulière à l'optimisation des performances du backend et du frontend. Les actions principales ont consisté à indexer les champs fréquemment interrogés de MySQL, à limiter la taille des réponses JSON via une pagination efficace, et à optimiser les calculs des statistiques et des indicateurs de dashboard pour réduire la latence des requêtes. Le frontend bénéficie également d'optimisations React natives (virtualisation des listes, memoization des composants, lazy-loading des pages) pour améliorer la réactivité de l'interface utilisateur.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
Le Sprint 3 conclut le développement du système GMAO, livrant une solution complète et fonctionnelle, prête pour un déploiement en conditions réelles. Les optimisations apportées aux performances, l'amélioration des interfaces utilisateur et la validation par le personnel de maintenance garantissent que le système répond aux exigences initiales d'automatisation de la gestion de maintenance et de réactivité opérationnelle. La documentation finalisée et l'infrastructure stabilisée facilitent une transition vers une phase de mise en œuvre effective, marquant une étape clé dans la modernisation de la gestion technique du parc informatique et des équipements.
