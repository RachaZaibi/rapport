\section{Objectifs et livrables}
\label{sec:objectifs_sprint1}

L'objectif principal du Sprint 1 est d'établir une infrastructure backend solide et fonctionnelle permettant la gestion complète des équipements informatiques et des processus d'exploitation associés. Cette phase vise à mettre en place un serveur d'application performant basé sur Express.js\cite{expressjs2024} et Sequelize\cite{sequelize2024}, et à configurer une base de données relationnelle capable de persister les données avec fiabilité et cohérence. Les cinq livrables clés de ce sprint sont :

\begin{itemize}
    \item \textbf{Backend API REST avec Express.js\cite{expressjs2024} et Sequelize ORM\cite{sequelize2024}} : Une API REST complète et documentée, implémentée avec Express.js, exposant 16 suites d'endpoints sécurisés couvrant les équipements, les tickets, les interventions, les maintenances, les installations, les licences et plus. L'API intègre une authentification JWT Bearer, une validation des entrées via Sequelize, une gestion d'erreurs robuste, et des logs structurés via Morgan.
    \item \textbf{Base de données relationnelle MySQL\cite{mysql2024} avec 18 modèles} : Une base de données MySQL avec un schéma complexe modélisant 18 entités métier incluant Équipement, Ticket, Intervention, Maintenance, Installation, Licence, Logiciel, Assignment, Transfer, Rapport, Bloc, Salle, et Département. Chaque modèle implémente des relations définies via Sequelize avec indices d'optimisation et contraintes d'intégrité.
    \item \textbf{Module de gestion des équipements avec CRUD avancé} : Un module complet implémentant 9 opérations pour les équipements (création, lecture, modification, suppression, historique, assignation, transfert, disposition). Chaque opération inclut la validation métier, le contrôle d'accès basé sur les rôles (RBAC), et la génération d'événements auditables.
    \item \textbf{Système de gestion des incidents et maintenances} : Un module pour la création et la gestion de tickets informatiques, des interventions associées, et des plans de maintenance préventive et corrective, avec assignation automatique des techniciens et suivi du statut.
    \item \textbf{Interface web intuitive et gestion des licences logicielles} : Une interface frontend React\cite{react2024} avec Material-UI\cite{materialui2024}, construite avec Vite\cite{vite2024}, offrant une authentification, gestion des utilisateurs, des licences logicielles, des installations et des transferts d'équipements, générant des rapports PDF/Excel et des statistiques.
\end{itemize}

Ces objectifs s'alignent avec les priorités M (Must have) du Product Backlog (voir Tableau \ref{tab:backlog}), en particulier les tâches M-01 « Gestion des équipements », M-02 « Gestion des incidents », M-03 « Gestion des maintenances », et M-06 « Stockage et historique des données », comme détaillé dans le chapitre précédent. Le périmètre du Sprint 1 couvre également les fonctionnalités S (Should have) pour assurer une base production-ready complète.

\section{Critères d'acceptation}
\label{sec:acceptance_criteria_sprint1}

Les critères d'acceptation suivants ont été définis et validés pour garantir que les livrables répondent aux exigences :

\subsection*{Contrôle d'accès basé sur les rôles (RBAC)}

Un système RBAC complet a été implémenté via le middleware \textit{checkPermission} :
\begin{itemize}
    \item Les utilisateurs disposent de rôles (administrateur, technicien, utilisateur) attribués à la création du compte
    \item Chaque endpoint protégé vérifie les permissions requises (canView, canCreate, canEdit, canDelete, canAssign, etc.)
    \item Les actions non autorisées retournent une réponse 403 (Forbidden) explicite
    \item Les administrateurs ont accès à toutes les fonctionnalités; les autres rôles ont des restrictions métier
\end{itemize}

\subsection*{Critère 1 : Opérations CRUD complètes sur les équipements via API}

Les opérations CRUD doivent fonctionner correctement via l'API REST avec authentification JWT :
\begin{itemize}
    \item Un équipement peut être créé en envoyant une requête POST à /api/equipements avec les paramètres obligatoires (numeroSerie, inventoryNumber, marque, modele, categorie, materialSource) et authentification JWT valide
    \item Un équipement existant peut être modifié en envoyant une requête PUT /api/equipements/:id avec les nouvelles valeurs
    \item Un équipement peut être assigné à un utilisateur via POST /api/equipements/:id/assign
    \item Un équipement peut être transféré à une nouvelle localisation via POST /api/equipements/:id/transfer
    \item Un équipement peut être marqué comme retiré via POST /api/equipements/:id/dispose
    \item Un équipement peut être supprimé via DELETE /api/equipements/:id
    \item L'historique de modification de chaque équipement est accessible via GET /api/equipements/:id/history
    \item Toutes les opérations retournent les codes HTTP appropriés et des messages d'erreur explicites en cas d'échec
    \item Les opérations non autorisées retournent 403 (Forbidden) avec justification
\end{itemize}

\subsection*{Critère 2 : Données persistées correctement en base}

Les données doivent être correctement stockées et récupérées de la base de données :
\begin{itemize}
    \item Les équipements créés sont visibles immédiatement après leur création via GET /api/equipment.
    \item Les modifications apportées à un équipement sont reflétées dans la base de données et visibles lors des requêtes ultérieures.
    \item Les équipements supprimés ne sont plus accessibles via l'API.
    \item Les données sont persistées même après un redémarrage du serveur.
    \item Les métadonnées (created\_at, updated\_at) sont correctement enregistrées.
\end{itemize}

\subsection*{Critère 3 : Interface web fonctionnelle avec gestion complète}

Une interface web sophistiquée a été développée pour visualiser et gérer les équipements :
\begin{itemize}
    \item Tableau de bord (Dashboard) avec statistiques clés (nombre d'équipements, tickets ouverts, maintenances prévues)
    \item Liste des équipements avec filtres avancés, recherche, tri et pagination
    \item Détails complets de chaque équipement incluant historique, tickets, maintenances, licences associées
    \item Formulaires d'ajout/modification avec validation côté client et serveur
    \item Gestion des incidents avec création de tickets et assignation aux techniciens
    \item Suivi des maintenances préventives et correctives avec calendrier
    \item Gestion des licences logicielles et des installations
    \item Génération de rapports PDF et exports Excel
    \item Authentification sécurisée avec JWT et gestion des permissions par rôle
    \item Thème adaptable (mode clair/sombre) et interface responsive
\end{itemize}

\subsection*{Critère 4 : Système de gestion des incidents intégré}

Un système complet de gestion des tickets d'incidents a été implémenté :
\begin{itemize}
    \item Création de tickets par les utilisateurs avec titre, description et priorité
    \item Assignation des tickets aux techniciens
    \item Suivi du statut (nouveau, en cours, fermé, réouvert) avec historique
    \item Enregistrement des interventions associées avec détails techniques
    \item Génération de rapports d'activité par technicien
\end{itemize}

\subsection*{Critère 5 : Gestion des maintenances et licences}

Des modules complémentaires pour maintenances et licences ont été intégrés :
\begin{itemize}
    \item Plans de maintenance préventive avec fréquences configurables
    \item Suivi des maintenances correctives liées aux interventions
    \item Gestion des licences logicielles avec dates d'expiration
    \item Suivi des installations logicielles sur les équipements
\end{itemize}

% Challenges and solutions
\section{Défis et solutions}
\label{subsec:defis_sprint1}

Plusieurs défis ont été rencontrés et résolus au cours du sprint :

\begin{enumerate}
    \item \textbf{Modélisation Sequelize complexe} : Les 18 entités avec relations polymorphes (one-to-many, many-to-many) ont présenté des défis de synchronisation. Solution : migrations progressives et fixtures de test.
    
    \item \textbf{Validation Sequelize} : Balancer entre rigueur et flexibilité dans la validation multi-niveaux. Solution : validateurs ORM + middleware d'entreprise.
    
    \item \textbf{JWT Bearer + RBAC} : Vérifier l'identité et les permissions sur chaque endpoint. Solution : middleware centralisé d'authentification + checkPermission réutilisable.
    
    \item \textbf{Requêtes N+1} : Eager loading de relations imbriquées. Solution : include Sequelize avec spécification des associations.
\end{enumerate}
