\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
\label{sec:intro_sprint1}

Ce chapitre est entièrement dédié au \textbf{Sprint 1}, qui constitue la première itération majeure dans le cycle de développement du système de gestion des équipements informatiques destiné au \textit{SmartLab} de la Faculté de Médecine de Monastir. Faisant suite à l'étude architecturale globale et respectant la planification de notre feuille de route (détaillée précédemment dans le Tableau \ref{tab:sprints}), ce premier jalon s'inscrit pleinement dans la méthodologie Agile Scrum adoptée pour ce projet.

L’objectif principal de ce sprint est de poser des fondations techniques fiables et évolutives. Des mécanismes de sécurité de base ont été implémentés dans le cadre de ce projet à une échelle locale. L’effort de développement s’articule ainsi autour de trois axes directeurs :
\begin{itemize}
    \item \textbf{La mise en place de l’infrastructure backend :} déploiement d’une architecture orientée services capable de centraliser la logique métier.
    \item \textbf{La persistance et la modélisation des données :} configuration et structuration de la base de données relationnelle afin de garantir l’intégrité des informations.
    \item \textbf{Le cœur fonctionnel initial :} implémentation du module de gestion des équipements (opérations CRUD, filtres adaptés et fonctionnalités d’importation).
\end{itemize}

Afin de soutenir ces objectifs et d'assurer une séparation claire des responsabilités (SOC - \textit{Separation of Concerns}), nous avons opté pour une \textbf{architecture découplée en 3 couches (3-Tier)} : une couche de Présentation (React.js), une couche Application \& Logique Métier (Express.js \& Sequelize), et une couche de Données (MySQL). 

La Figure \ref{fig:architecture_sprint1} détaille la cartographie de cette architecture technique sous forme de niveaux (Tiers), mettant en exergue l'alignement des flux et l'intégration des différents modules développés lors de cette itération.

\label{sec:objectifs_sprint1}

L’objectif principal du Sprint 1 est d’établir une infrastructure backend fiable permettant la gestion des équipements informatiques et des processus d’exploitation associés. Cette phase vise à mettre en place un serveur d’application efficace basé sur Express.js\cite{expressjs2024} et Sequelize\cite{sequelize2024}, ainsi qu’à configurer une base de données relationnelle capable de persister les données avec fiabilité et cohérence. Les cinq livrables clés de ce sprint sont :

\begin{itemize}
    \item \textbf{Backend API REST avec Express.js\cite{expressjs2024} et Sequelize ORM\cite{sequelize2024}} : Une API REST fonctionnelle et documentée, implémentée avec Express.js dans le cadre de ce projet, exposant 16 suites d'endpoints protégés couvrant les équipements, les tickets, les interventions, les maintenances, les installations, les licences et plus. Des mécanismes de sécurité de base ont été implémentés, notamment l’authentification JWT et le contrôle d’accès basé sur les rôles (RBAC). L'API intègre également une validation des entrées via Sequelize, une gestion d'erreurs fiable, et des logs structurés via Morgan.
    \item \textbf{Base de données relationnelle MySQL\cite{mysql2024} avec 17 modèles} : Une base de données MySQL avec un schéma modélisant 17 entités métier incluant Équipement, Ticket, Intervention, Maintenance, Installation, Licence, Logiciel, Affectation, Transfert, Rapport, Bloc, Salle et Département, implémenté de manière simplifiée à une échelle locale. Chaque modèle définit des relations via Sequelize, avec des index d’optimisation et des contraintes d’intégrité.
    \item \textbf{Module de gestion des équipements avec CRUD adapté} : Un module fonctionnel implémentant 9 opérations pour les équipements (création, lecture, modification, suppression, historique, affectation, transfert, disposition). Chaque opération inclut la validation métier, le contrôle d'accès basé sur les rôles (RBAC), et la génération d'événements auditables.
    \item \textbf{Système de gestion des incidents et maintenances} : Un module pour la création et la gestion de tickets informatiques, des interventions associées, et des plans de maintenance préventive et corrective, avec affectation automatique des techniciens et suivi du statut.
    \item \textbf{Interface web intuitive et gestion des licences logicielles} : Une interface frontend React\cite{react2024} avec Material-UI\cite{materialui2024}, construite avec Vite\cite{vite2024}, offrant une authentification, gestion des utilisateurs, des licences logicielles, des installations et des transferts d'équipements, générant des rapports PDF/Excel et des statistiques.
\end{itemize}

Ces objectifs s'alignent avec les priorités M (Must have) du Product Backlog (voir Tableau \ref{tab:backlog}), en particulier les tâches M-01 « Gestion des équipements », M-02 « Gestion des incidents », M-03 « Gestion des maintenances », et M-06 « Stockage et historique des données », comme détaillé dans le chapitre précédent. Le périmètre du Sprint 1 couvre également les fonctionnalités S (Should have) pour assurer une base fonctionnelle. Certaines entités ont été préparées dès les premiers sprints afin de faciliter leur intégration progressive dans les itérations suivantes.

\subsubsection{Champs étendus pour les équipements}

Le modèle Équipement enrichit l'inventaire standard avec plusieurs attributs :

\begin{itemize}
    \item \textbf{numeroSerie} : Identifiant fabricant (unique, obligatoire)
    \item \textbf{inventoryNumber} : Numéro d'inventaire interne (unique, obligatoire)
    \item \textbf{codeQR} : Code QR pour suivi rapide via scanner (stocké en chaîne de caractères)
    \item \textbf{marque} et \textbf{modele} : Identifiants commerciaux
    \item \textbf{categorie} : Classification de l'équipement (ex: PC, Imprimante, Serveur - chaîne de caractères)
    \item \textbf{etat} : État opérationnel (fonctionnel, en\_panne, en\_réparation, réformé)
    \item \textbf{materialSource} : Provenance, selon l'ENUM réel \texttt{title\_1}, \texttt{title\_2}, \texttt{donation}, \texttt{other}
    \item \textbf{currentStatus} et \textbf{currentHolderType} : Localisation courante
    \item \textbf{dateAchat} : Date d'acquisition
    \item \textbf{assignedAt} : Timestamp de la dernière affectation
\end{itemize}

\textbf{Note importante} : Les champs \textit{codeQR} et \textit{categorie} sont stockés comme chaînes 
de caractères pour simplifier la gestion. Une future évolution pourrait les promouvoir en entités 
séparées si un suivi granulaire devient nécessaire.

\subsection{Développement de l’API REST et Architecture des Endpoints}
\label{subsec:api_rest_sprint1}

Sur la base des modèles de données et des relations conceptuelles établis en amont, dans le cadre de ce projet à une échelle locale, une API REST (Representational State Transfer) fiable et découplée a été développée. L’implémentation de cette interface de programmation s'appuie sur le framework Express.js, permettant une gestion efficace et asynchrone des requêtes HTTP.

Afin de structurer les échanges entre la couche de présentation (React.js) et le serveur, chaque entité métier dispose d’un ensemble d'endpoints (points d'accès) standardisés. Ces derniers respectent rigoureusement les conventions REST et s'appuient sur les verbes HTTP sémantiques (\texttt{GET}, \texttt{POST}, \texttt{PUT}, \texttt{PATCH}, \texttt{DELETE}) pour expliciter la nature de l'action requise :
\begin{itemize}
    \item \textbf{\texttt{GET}} : Utilisé exclusivement pour la récupération protégée de ressources ou de collections, sans altération de l'état du système.
    \item \textbf{\texttt{POST}} : Dédié à la création de nouvelles instances au sein de la base de données.
    \item \textbf{\texttt{PUT}} : Exploité pour la mise à jour globale et idempotente d'une ressource existante.
    \item \textbf{\texttt{PATCH}} : Privilégié pour les modifications partielles ou chirurgicales, telles que le changement d'état d'un matériel informatique ou la validation d'un transfert.
    \item \textbf{\texttt{DELETE}} : Réservé à la suppression logique ou physique d'une entrée.
\end{itemize}

\subsection{Mécanismes transverses : sécurité, validation et cycle de vie}
\label{subsec:endpoints_transverses}

Au-delà de la simple exposition des données, l'accès à ces ressources est gouverné par une suite de middleware s'exécutant de manière séquentielle lors du cycle requête-réponse :

\begin{enumerate}
    \item \textbf{Couche d'Authentification (JWT) :} Validation de l'intégrité du jeton d'accès présent dans l'en-tête de la requête (\textit{Authorization Header}). Ce mécanisme permet de vérifier que l'appelant possède une session active et reconnue par le système.
    \item \textbf{Couche d'Autorisation (RBAC - Role-Based Access Control) :} Contrôle des privilèges de l'utilisateur. Alors que les opérations de lecture (\texttt{GET}) sont accessibles à l'ensemble du personnel technique authentifié, les routes d'écriture (\texttt{POST}, \texttt{PUT}, \texttt{DELETE}) exigent explicitement des permissions administratives strictes (ex: Administrateur du SmartLab).
    \item \textbf{Couche de Validation Métier :} Avant toute persistance via l'ORM Sequelize, les données reçues au format JSON sont interceptées et validées (vérification des types, des champs obligatoires et des formats). En cas de non-conformité, l'API rejette immédiatement la requête en retournant un code d'état HTTP \texttt{400 Bad Request}, contribuant ainsi à préserver l'intégrité de la base de données MySQL.
\end{enumerate}

Chaque transaction se clôture par l'émission d'une réponse JSON standardisée, adossée aux codes de statut HTTP appropriés (\texttt{200 OK}, \texttt{201 Created}, \texttt{401 Unauthorized}, \texttt{403 Forbidden}), assurant ainsi une résilience adaptée et une communication fluide avec l'application frontend React.js.

\section{Critères d'acceptation}
\label{sec:acceptance_criteria_sprint1}

Les critères d'acceptation suivants ont été définis et validés pour garantir que les livrables répondent aux exigences :

\subsection*{Contrôle d'accès basé sur les rôles (RBAC)}

Un système RBAC fonctionnel a été implémenté via le middleware \textit{checkPermission}, dans le cadre des mécanismes de sécurité de base du prototype :
\begin{itemize}
    \item Les utilisateurs disposent de rôles (administrateur, technicien, utilisateur) attribués à la création du compte
    \item Chaque endpoint protégé vérifie les permissions requises (canView, canCreate, canEdit, canDelete, canAssign, etc.)
    \item Les actions non autorisées retournent une réponse 403 (Forbidden) explicite
    \item Les administrateurs ont accès à toutes les fonctionnalités; les autres rôles ont des restrictions métier
\end{itemize}

\subsection*{Critère 1 : Opérations CRUD fonctionnelles sur les équipements via API}

Les opérations CRUD doivent fonctionner correctement via l'API REST avec authentification JWT :
\begin{itemize}
    \item Un équipement peut être créé en envoyant une requête POST à /api/equipements avec les paramètres obligatoires (numeroSerie, inventoryNumber, marque, modele, categorie, materialSource) et authentification JWT valide
    \item Un équipement existant peut être modifié en envoyant une requête PUT /api/equipements/:id avec les nouvelles valeurs
    \item Un équipement peut être affecté à un utilisateur via POST /api/equipements/:id/assign
    \item Un équipement peut être transféré à une nouvelle localisation via POST /api/equipements/:id/transfer
    \item Un équipement peut être marqué comme retiré via POST /api/equipements/:id/dispose
    \item Un équipement peut être supprimé via DELETE /api/equipements/:id
    \item L'historique de modification de chaque équipement est accessible via GET /api/equipements/:id/history
    \item Toutes les opérations retournent les codes HTTP appropriés et des messages d'erreur explicites en cas d'échec
    \item Les opérations non autorisées retournent 403 (Forbidden) avec justification
\end{itemize}

\subsection*{Critère 2 : Données persistées correctement en base}

Les données doivent être correctement stockées et récupérées de la base de données :
\begin{itemize}
    \item Les équipements créés sont visibles immédiatement après leur création via GET /api/equipment.
    \item Les modifications apportées à un équipement sont reflétées dans la base de données et visibles lors des requêtes ultérieures.
    \item Les équipements supprimés ne sont plus accessibles via l'API.
    \item Les données sont persistées même après un redémarrage du serveur.
    \item Les métadonnées (created\_at, updated\_at) sont correctement enregistrées.
\end{itemize}

\subsection*{Critère 3 : Interface web fonctionnelle avec gestion adaptée}

Une interface web adaptée a été développée pour visualiser et gérer les équipements :
\begin{itemize}
    \item Tableau de bord avec statistiques clés (nombre d'équipements, tickets ouverts, maintenances prévues)
    \item Liste des équipements avec filtres adaptés, recherche, tri et pagination
    \item Détails fonctionnels de chaque équipement incluant historique, tickets, maintenances, licences associées
    \item Formulaires d'ajout/modification avec validation côté client et serveur
    \item Gestion des incidents avec création de tickets et affectation aux techniciens
    \item Suivi des maintenances préventives et correctives avec calendrier
    \item Gestion des licences logicielles et des installations
    \item Génération de rapports PDF et exports Excel
    \item Authentification JWT et gestion des permissions par rôle, dans le cadre de mécanismes de sécurité de base
    \item Thème adaptable (mode clair/sombre) et interface responsive
\end{itemize}

\subsection*{Critère 4 : Système de gestion des incidents intégré}

Un prototype fonctionnel de gestion des tickets d'incidents a été implémenté :
\begin{itemize}
    \item Création de tickets par les utilisateurs avec titre, description et priorité
    \item Affectation des tickets aux techniciens
    \item Suivi du statut (nouveau, en cours, fermé, réouvert) avec historique
    \item Enregistrement des interventions associées avec détails techniques
    \item Génération de rapports d'activité par technicien
\end{itemize}

\subsection*{Critère 5 : Gestion des maintenances et licences}

Des modules complémentaires pour maintenances et licences ont été intégrés :
\begin{itemize}
    \item Plans de maintenance préventive avec fréquences configurables
    \item Suivi des maintenances correctives liées aux interventions
    \item Gestion des licences logicielles avec dates d'expiration
    \item Suivi des installations logicielles sur les équipements
\end{itemize}

La validation du Sprint 1 a été réalisée par des tests fonctionnels manuels via l'interface Swagger UI et l'interface web React. Swagger UI a permis de parcourir largement les endpoints CRUD exposés, de vérifier les paramètres obligatoires, les codes HTTP retournés et les effets attendus en base, tandis que l'interface web a validé les parcours de consultation, création, modification, transfert et affectation d'équipements. % Challenges and solutions
\section{Défis et solutions}
\label{subsec:defis_sprint1}

Plusieurs défis ont été rencontrés et résolus au cours du sprint :

\begin{enumerate}
    \item \textbf{Modélisation Sequelize complexe} : Les 17 modèles avec relations variées (one-to-many, many-to-many) ont présenté des défis de synchronisation. Solution : migrations progressives et fixtures de test.
    
    \item \textbf{Validation Sequelize} : Trouver un équilibre entre rigueur et flexibilité dans la validation multiniveau. Solution : validateurs ORM et middleware métier.
    
    \item \textbf{JWT Bearer + RBAC} : vérifier l'identité et les permissions sur chaque endpoint dans le cadre de mécanismes de sécurité de base. Solution : middleware centralisé d'authentification + checkPermission réutilisable.
    
    \item \textbf{Requêtes N+1} : Eager loading de relations imbriquées. Solution : include Sequelize avec spécification des associations.
\end{enumerate}

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
\label{sec:conclusion_sprint1}

Le Sprint 1 a établi une infrastructure fonctionnelle avec Express.js\cite{expressjs2024} + Sequelize\cite{sequelize2024} (17 modèles persistants), des mécanismes de sécurité de base incluant l’authentification JWT et le RBAC, et une interface React\cite{react2024} + Material-UI\cite{materialui2024} construite avec Vite\cite{vite2024}, implémentée dans le cadre de ce projet de fin d’études. Les critères fonctionnels couvrant les équipements, les incidents, les maintenances et les licences ont été validés par des tests fonctionnels manuels.

Le Sprint 1 fournit ainsi une base fiable. Le Sprint 2 se concentrera sur les notifications Firebase FCM dans une version adaptée au cadre académique, la gestion des tickets et les fonctionnalités de maintenance. La solution reste alignée avec les objectifs du SmartLab à une échelle locale.
